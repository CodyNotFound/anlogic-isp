# 安路赛题二 FPGA 工程整体架构与备赛开发手册

版本：v1.0（2026-09-12）

## 先说结论

你的工程最稳的组织方式，不是把 Lab1、Lab2、Lab3 三份工程直接拼在一起，而是：

1. 以 Lab1 作为“永远可回退”的视频基线；
2. 把 Lab2 的边缘检测、Lab3 的 OSD 拆成独立功能模块；
3. 顶层只负责连接，不负责算法；
4. 把 MIPI、DDR、HDMI、PLL 和约束视为平台层，尽量不动；
5. 用统一的视频流接口接入灰度、Sobel、颜色检测、帧差和 OSD；
6. 用 Git 分支和可验证里程碑管理每次变化。

这样做的目的，是让你以后新增功能时“加模块、接接口、写测试”，而不是继续把代码堆进一个越来越长的 `design_top_wrapper.v`。

## 一、三个官方例程分别应该怎么用

### Lab1：基线工程

目录：`lab_ex1_mipi_hdmi_SC500_720P`

它完成的是：

```text
SC500CS
 → 2-lane MIPI D-PHY
 → CSI-2 解包
 → RAW10 解包
 → ISP（去马赛克、BLC、AWB 等）
 → DDR2 帧缓存/跨时钟
 → HDMI 时序和发送
```

当前统一配置是 1280×720@60fps。Lab1 另外保留了 1920×1080@30fps 寄存器表，但不要在第一阶段切换。Lab1 的价值是“先证明板卡、摄像头、DDR、HDMI 都正常”。

### Lab2：算法参考

目录：`lab_ex2_edge_SC500_720P`

它没有重写整条视频链路，而是在 ISP 中加入 `edge_detect_96.v`。这说明边缘检测应该属于 ISP/算法层，而不是写进顶层或 HDMI 发送器。

你可以借用它的窗口/行缓存/流水线思路，但把模块重命名、整理端口，并给它独立的仿真测试。

### Lab3：显示叠加参考

目录：`lab_ex3_osd_SC500_720P`

它加入 `osd_char_lib.v`，并在 `hdmi_mixer.v` 中完成字符、Logo 或状态信息叠加。OSD 属于显示合成层，应该放在 DDR 读出、HDMI 输出之前，不能把字符 ROM 和算法统计散落到各处。

## 二、建议的总数据流

```text
                ┌──────────────┐
                │ SC500 配置    │← I2C/27MHz
                └──────┬───────┘
                       ▼
                ┌──────────────┐
                │ MIPI D-PHY RX │  平台层
                └──────┬───────┘
                       ▼
                ┌──────────────┐
                │ CSI/RAW10解包 │
                └──────┬───────┘
                       ▼
                ┌──────────────┐
                │ ISP 基础链    │ BLC/demosaic/AWB
                └──────┬───────┘
                       ▼ RGB888
       ┌───────────────┴────────────────┐
       ▼                                ▼
┌───────────────┐                ┌───────────────┐
│ 算法处理链     │                │ 统计/测量链    │
│ 灰度/Sobel     │                │ 帧差/颜色/坐标 │
│ 颜色检测       │                │ fps/延迟/FIFO  │
└───────┬───────┘                └───────┬───────┘
        └──────────────┬─────────────────┘
                       ▼
                ┌──────────────┐
                │ OSD 合成      │ Logo/框/文字/状态
                └──────┬───────┘
                       ▼
                ┌──────────────┐
                │ DDR2 帧缓存   │
                └──────┬───────┘
                       ▼
                ┌──────────────┐
                │ HDMI 输出     │ 1280×720@60
                └──────────────┘
```

这里有一个很重要的设计选择：算法结果和统计结果分开。比如颜色检测可以输出目标框坐标，OSD 再决定是否画框；不要让颜色检测模块直接生成 HDMI 像素，这样未来换成帧差或形状检测时不会互相缠住。

│  ├─ overlay/                     # OSD、字体、Logo、状态栏

官方例程可以保留在 `[LOCAL_PATH]`，不建议整套复制到 GitHub。仓库只记录版本、来源和差异，避免把几百 MB 的 TD 日志、DDR 网表和临时文件提交进去。

## 四、每一层具体负责什么

### 1. 平台层：先稳定，少改

包括：

- `mipi_dphy_rx`；
- CSI-2/RAW10 解包；
- SC500 I2C 初始化和寄存器表；
- PLL、DDR2、FIFO；
- `video_in`、`video_out`；
- HDMI 时序、PHY 和发送。

平台层的问题通常表现为黑屏、花屏、错位、丢帧、DDR 溢出、MIPI 无数据。遇到这些问题时，不要同时加入新算法，否则无法判断故障来自哪里。

### 2. ISP 层：像素到像素的处理

ISP 负责把 RAW10 变成可以显示和计算的 RGB888，并执行逐像素或局部窗口算法。Sobel、灰度、滤波适合放这里。

ISP 模块要说明：

- 输入格式和位宽；
- Bayer 排列；
- 是否需要 3×3 窗口；
- 输出延迟多少拍；
- 行缓存深度；
- `valid/sof/eol` 如何同步。

### 3. Analytics 层：只产生结果，不画图

颜色检测可以输出：`target_valid`、`x_min`、`x_max`、`y_min`、`y_max`、`center_x`、`center_y`、`count`。

帧差可以输出：运动掩码、运动像素计数、活动区域。统计模块可以输出：帧率、处理延迟、FIFO 高水位、溢出/下溢计数。

这些结果由 OSD 层显示，由控制层决定是否启用。

### 4. Overlay 层：显示合成

OSD 接收视频像素、当前坐标、目标框和状态数据，输出最终 RGB。Lab3 的 `osd_char_lib.v` 可以作为字体参考，但建议把字体 ROM、字符定位和状态栏分开。

### 5. Control 层：统一处理按键

按键只做三件事：消抖、产生一次性事件、修改参数寄存器。不要让按键直接穿透到多个算法模块。推荐模式：

```text
KEY_MODE  → NORMAL / SOBEL / COLOR / FRAME_DIFF
KEY_UP/DOWN → 阈值或灵敏度
KEY_OK     → OSD/调试信息开关
```

## 五、统一接口，避免以后乱套

建议所有自有视频模块采用统一的命名：

```verilog
s_valid, s_sof, s_eol, s_data
m_valid, m_sof, m_eol, m_data
```

如果模块有 ready，再增加 `s_ready/m_ready`。如果官方链路没有 ready，就用固定延迟适配器统一起来。

最容易翻车的地方是：算法只延迟了 `data`，没有同步延迟 `valid`、帧首、行尾或坐标。结果可能是图像看起来“有内容”，但边缘、框和文字在画面上漂移一拍或一行。

## 六、功能开关怎么设计

不要在十几个文件里散落：

```verilog
if (mode == 2'd1) ...
if (debug == 1'b1) ...
if (threshold > 8'd120) ...
```

建议把功能分成两类：

### 编译期参数

例如是否综合 Sobel、是否保留帧差模块、图像宽高、像素位宽。它们放在 `project_config.vh` 或顶层参数中。

### 运行期参数

例如算法模式、颜色阈值、OSD 开关、框线颜色、调试页面。它们放入 `param_bank`，按键或串口只修改这个参数块。

## 七、按阶段开发，任何阶段都能交付

| 阶段 | 目标 | 通过标准 |
|---|---|---|
| 0 | 点灯、下载、串口 | JTAG 稳定，LED/串口正常 |
| 1 | Lab1 原样运行 | 720p60 连续显示 30 分钟 |
| 2 | 灰度/单一 Sobel | 画面连续，边缘位置正确 |
| 3 | Lab3 OSD | Logo、模式名、帧率显示正确 |
| 4 | 颜色目标检测 | 红/蓝/黄目标框和坐标稳定 |
| 5 | 帧差运动检测 | 移动物体能检测，静止时误报可控 |
| 6 | 模式切换 | 按键切换不黑屏、不死机 |
| 7 | 指标和稳定性 | 延迟、fps、FIFO、资源、时序有记录 |

每个阶段建立一个 Git tag，例如 `v0.1-baseline`、`v0.2-sobel`、`v0.3-osd`。比赛现场优先带经过长时间运行验证的 tag，不要带当天刚改完的工作区。

## 八、GitHub 协作规则

### 分支

- `main`：可提交、可复现、可演示；
- `develop`：集成分支；
- `feature/sobel`、`feature/osd`、`feature/color-detect`：单功能；
- `fix/mipi-reset`、`fix/fifo-underflow`：问题修复；
- `hw/hx1p35a-pin`：硬件和约束变化。

### 提交

每次提交只做一件事，示例：

```text
platform: freeze SC500 720p60 baseline
isp: add 3x3 sobel pipeline
overlay: show mode and fps
control: add debounced mode key
sim: add frame boundary checks
docs: record 2-hour stability test
```

### 不要提交

- `*_Runs/` 大量综合缓存；
- `log/` 全部日志；
- 临时波形和用户目录绝对路径；
- 任何无法由源文件重新生成的无关中间物。

建议提交：`.al`、`pin.adc`、`.sdc`、IP 参数、必要的 IP wrapper、源文件列表、仿真脚本和关键报告摘要。

## 九、如何做到“新增功能不翻车”

新增一个功能时，严格按这 8 步：

1. 写一页功能说明：输入、输出、时钟、延迟、资源预算；
2. 在 `rtl/` 对应层新建独立目录；
3. 先写模块级仿真或测试图；
4. 用统一视频流接口连接；
5. 在 `mode_ctrl` 增加开关，不改其他模块内部状态；
6. 在 OSD 显示开关、状态和错误计数；
7. 综合、检查时序和资源；
8. 通过实板长时间运行后再合并到 `develop`。

这样做的好处是，某个新功能失败时可以关闭它，系统仍回退到上一个稳定版本。

## 十、最重要的故障排查顺序

### 黑屏

先回到 Lab1 tag，检查供电、27MHz、摄像头复位、I2C 地址 `0x36`、MIPI 排线、HDMI 线和 PLL lock。

### 花屏/错位

先看 RAW10 解包、lane 配置、像素时钟、`valid/sof/eol` 对齐和 DDR/FIFO 水位，再看算法。

### OSD 文字错位

检查 HDMI 像素坐标、字体行列计数、颜色合成优先级，以及 OSD 与视频数据是否同拍。

### 运行一段时间后出错

检查 FIFO 高水位、DDR 写读忙信号、帧指针、复位跨时钟同步、温度和供电。不要只重新下载 bit 文件后继续演示，要把错误计数和根因记入 `docs/decision-log.md`。

## 十一、比赛前必须准备的证据

- 1280×720@60fps 的现场视频；
- Sobel、颜色检测、帧差和 OSD 的模式切换视频；
- 资源占用和时序报告；
- 实测处理延迟；
- 连续运行 2 小时记录；
- 失败回退版本和备份 bit 文件；
- 一页系统框图和一页创新点说明。

## 十二、最终建议

现在最合理的工程动作是：复制 Lab1 为基线，先不要改 MIPI、DDR 和 HDMI；把 Lab2 的边缘模块整理到 `rtl/isp`，把 Lab3 的 OSD 整理到 `rtl/overlay`，再在两者之间建立统一的视频流接口。等这条链路稳定后，再增加颜色目标检测、帧差和模式控制。

你的项目最终应该像一个“平台 + 可插拔算法 + 可插拔显示 + 可验证指标”的系统，而不是一份不断追加代码的例程副本。
